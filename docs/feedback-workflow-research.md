# Feedback workflow research

Date: 2026-11-22. Primary-source findings only. **Evidence** summarizes retrieved sources; **Decision** specifies this product's design, not a requirement attributed to those sources.

## Questions belong to their chat

**Evidence:** Claude Code documents `AskUserQuestion` as multiple-choice clarification or decision gathering, with an `Other` row or notes field for free text. Questions wait for an answer by default. Its optional idle timeout does not apply to background sessions, screen reader mode, or Remote Control. Permission prompts, including plan approval, never auto-resolve on idle. [1]

**Decision:** Render each agent question inline in its owning chat, next to the conversation that explains it. Keep questions and answers associated with the originating session and request; switching chats must not redirect an answer. Preserve choices, free-text input, and pending state until an explicit answer or cancellation. Background questions may expose an unread/pending indicator, not steal focus or open a global modal. Keep clarification separate from permission and plan approval.

**Boundary:** [1] supports explicit conversational clarification and free-text answers. It does not prescribe inline placement, cross-session routing, or a ban on question modals. Those are product decisions to retain context and avoid interrupting another chat.

## Plan in the right sidebar

**Evidence:** CSSWG's scroll-anchoring draft describes unexpected movement during content consumption as disruptive. Its mechanism adjusts scroll position to keep the user's view stable across layout changes. This is an Editor's Draft, explicitly work in progress, not a browser-support guarantee or a specification of streaming-chat behavior. [2]

**Decision:** Show the owning chat's plan in a labeled right sidebar. Reveal streamed plan content progressively without replacing the chat or opening a modal. Give the plan its own scroll container; updates must not scroll the conversation.

**Decision:** Follow appended plan content only while the user remains at the plan's end. Scrolling away suspends following and preserves the reading position; offer an explicit “Jump to latest” control to resume. Do not reset to the top or force the bottom for every token, render, or status change. Opening the panel may preserve its previous position; merely receiving an update must not move keyboard focus. Keep plan approval an explicit action, separate from revealing or scrolling the plan.

**Boundary:** Right-side placement, follow-at-end behavior, and the resume control are product decisions informed by [2]'s stability goal. Native scroll anchoring alone does not implement this intent policy. Progressive reveal means content arrival, not mandatory smooth animation.

## Compact quick setup dialogs

**Evidence:** WAI APG's modal-dialog pattern makes the background inert, moves focus inside on open, contains `Tab` and `Shift+Tab`, and closes on `Escape`. It strongly recommends a visible close or cancel button. The dialog needs an accessible name and `aria-modal="true"`; modal semantics must match actual interaction blocking. [3]

**Evidence:** Initial focus depends on content: usually the first focusable control, but a static heading or introductory element can be appropriate for structured or long content. Closing normally returns focus to the invoker; if it disappeared, or the next workflow step is more logical, focus moves to a suitable alternative. APG advises omitting `aria-describedby` for complex structured content rather than announcing it as one unbroken string. [3]

**Decision:** Use compact, viewport-centered modals for short, user-invoked quick setup tasks. Keep only task-relevant controls, a clear title, primary action, and visible cancel/close action. Bound dimensions to the viewport; allow internal scrolling when needed rather than clipping controls. Centering and compactness are product choices, not APG requirements.

**Decision:** On open, focus the first meaningful setup field unless introductory content must be read first. Trap keyboard traversal and make background controls inert. On cancel or completion, restore the launcher focus, or the logical next control if the launcher no longer exists. Do not mark the plan sidebar or inline questions modal. Do not introduce a second nested modal for ordinary setup steps.

## Implemented workflow contract

Questions replace the owning chat's composer, never the scrollable transcript or another tab: `ask`, `askDialog`, `form`, non-permission `select`, and non-sign-in `input`. Their request-owned drafts and receipt timestamps survive remounts. Permission confirmations and sign-in remain explicit modal interactions.

Plan documents and structured approval render only in the inspector. A focused project/session reveals its plan on activation, a new planning turn, or a new proposal. Deliberately closing the inspector wins through refreshes and completion of that turn; a subsequent planning turn or proposal may reveal it again. Background sessions cannot reveal their plan over the focused project. The sidebar does not move keyboard focus.

The plan previews completed prefixes of actual streamed write arguments targeting its exact path or `propose`. Persisted snapshots reconcile after tool/turn events and at a bounded 400 ms cadence during active planning; the known path avoids repeated mode RPCs. No synthetic typing animation or claim that disk writes arrive per token. Follow-scroll stops on upward reading gestures and resumes only at the end or through Jump to latest.

Plan review has a fixed footer. To refine, select a passage, save a comment and explicitly choose Refine. Multiple quoted comments are sent together. Mermaid in Markdown uses the same renderer as chat. Subagent transcripts open inside their chat pane; the tab strip is reserved for top-level sessions. To-Do is a separate drop-down below the tab strip.

All transcript starter cards use a single compact prompt-editing dialog. Continue in chat stages the draft through the existing composer path, retaining normal attachments and submission safeguards. Vibe, Goal and Loop use the same centered modal convention rather than workspace navigation. The plan itself is never rendered inside those setup dialogs.

Headless renderer tests cover request scope and draft restoration, scoped subagent and To-Do actions, streamed plan rendering, tab transitions and plan approval. An isolated Windows Electron session with a local protocol fixture verified the composer, model picker, Modes bounds, automatic Plan inspector reveal, queue RPC routing and absence of an embedded browser. No authenticated provider or Chrome profile was used.

## Session resume and protocol routing evidence

`showView` changes the focused runtime synchronously, settles the main route before awaiting hydration, and retains that runtime's history. Main-process `setTabView` synchronously wires full event streams for every visible tab, not only the focused pane; hidden tabs retain lightweight status and message-only continuity, without mounting a transcript. Returning A after A to B to A therefore need not wait for a transcript RPC to display retained history or receive new A events. Hydration previously deferred applying `get_state` and reasserting the subagent subscription until the complete transcript returned. These now settle independently; event-version guards still reject snapshots overtaken by fresh events.

Measurement, Bun on this workstation: 5,000 alternating committed user/assistant messages with repeated task/implementation prose, approximately 4 MB of text. Reconciling a structured clone took 2.15 ms; compact rows plus stable keys took 23.37 ms. Existing reconciliation replaced the array and first object even when text was unchanged. This does not demonstrate the reported 4 to 5 second production delay; no production timing validation was performed and no speculative transcript cache was added. Regression coverage observes retained A history and real streaming presentation from newly reduced A events while A's transcript remains unresolved.

Further root-path evidence: the sidecar `get_transcript_page` reconstructs the full display transcript before slicing every page; the GUI previously requested 256 rows per page, multiplying full-history construction by page count. The GUI now first requests the already-supported full `get_transcript` snapshot. An actual error response, including the sidecar's explicit transport-limit error, falls back to paged transport; no compatibility timeout or synthetic delay is introduced. A backend-source fixture using `buildSessionContext` with 5,000 linked alternating user/assistant entries measured 20 repeated builds at 32.73 ms versus one build at 0.84 ms, both yielding 5,000 complete messages. This isolates construction work, excludes serialization/network/DOM timing, and still does not prove the observed production delay's magnitude. The fixture ran against the available `/home/smokeyduck132/work/omp-sync` source checkout; the `/tmp/omp-src` checkout could not resolve its pi-tui dependency.

Protocol Auto preserves an omitted provider API when the sidecar permits it and materializes concrete APIs on explicit models. Saved-provider routes come from existing `get_available_models` metadata, including protocols already resolved by proxy discovery. The discovery RPC itself does not return `api`; merely adding a field to the GUI type cannot recover it. Without saved metadata, exact native `api.openai.com` uses Responses, exact `api.anthropic.com` uses Messages, and generic compatible endpoints use Chat Completions. A model called OpenAI or Claude through an arbitrary gateway does not prove that gateway accepts Responses or Messages. Every per-model explicit override wins; the effective Auto route is shown inline. Non-proxy discovery requires a concrete provider fallback under the sidecar's current schema.

Auto with a non-proxy automatic discovery type must save a concrete provider fallback because the sidecar only enables those discovery types when provider `api` exists. Reopening shows that concrete protocol rather than Auto; no unsupported configuration marker is written. Runtime-discovered models appear separately from configured rows, remain automatic when untouched, and only an edited discovered row becomes an explicit saved model override. Saved catalog protocol metadata is ignored after that row's effective endpoint changes.

## Split, focus and running-session performance evidence

The reported live 5–6 second split and 8–10 second synchronization delays are accepted observations, not reproduced production measurements. Source tracing found avoidable work and a separate partial-stream correctness gap:

- Drag/drop calls the existing tabs-store route, then main's `setTabView` changes full-stream coverage synchronously. The main `RpcClient` already correlates concurrent commands by request id; it does not serialize every RPC behind one request. No transport retry, timeout, delay or new persistent transcript cache was added.
- Every focus change previously reissued the complete hydration bundle, including a full transcript, even when both split panes had remained visible and fully subscribed. Hydration is now single-flight per runtime, session generation and current event version. A pane skips focus-only hydration only after its core snapshot succeeded and full-event coverage remained uninterrupted. Hiding invalidates both the hot marker and any in-flight snapshot before another route can supersede its return. Hidden returns still need a full refresh; failures remain retryable through the normal next activation.
- A restart can reuse the same session id. Runtime generations invalidate old snapshots before they start side effects or publish. The light starting/restarting status and full starting frame may both increment the generation: both belong to the same ordered process lifecycle before ready, so neither can make an earlier snapshot current again. Session replacement creates a new runtime; guards also compare runtime identity.
- A hidden sidecar previously dropped all message deltas although its committed transcript excludes the unfinished assistant response. Main now forwards only message start/update/end and pending plan proposals for ready parked processes. Their bounded runtime buffers update without mounting a transcript; terminal light statuses retire abandoned streams. Ready metadata never clears a visible pane's good partial text, and an already-ready parked metadata update is not treated as terminal.

Offline service-path fixture: 6,000 synthetic committed messages, 3,719,687 encoded bytes per transcript; actual `SidecarPool`, request-correlating `RpcClient`, React `useRpcEvents`, hydration and runtime stores; fake sidecar and in-memory command responses, React DOM/linkedom, no real profile, process, filesystem history, Electron IPC or provider traffic. Before/after aggregate artifacts are `test-results/session-performance/before.json` and `after.json` (ignored local evidence):

| Scenario | Before | After |
| --- | --- | --- |
| Three overlapping cold hydrations | 3 transcript decodes; 11,159,061 bytes | 1 decode; 3,719,687 bytes |
| Six focus changes inside the same visible pair | 6 transcript decodes; 22,318,122 bytes; 6 message publishes | no hydration commands, decodes or message publishes |
| 500 parked message deltas | no foreground renders, but only 8 of 3,508 expected partial characters survived return | no foreground renders; all 3,508 partial characters survived |
| Hidden return / cold partner | one full transcript still required | one full transcript still required |

Timings are not uniformly faster: overlapping cold hydration was 22.13 → 31.73 ms, cold split partner 13.65 → 72.69 ms, six warm focus changes 52.89 → 18.24 ms, hidden return 7.31 → 16.88 ms. Retaining formerly dropped parked deltas does real additional work (0.55 → 31.00 ms for the 500-delta burst). These synthetic service timings establish neither live latency nor a guaranteed speedup.

A separate actual headless Chromium/CSS integration used `TabBar` HTML drag/drop, `SplitWorkspace`, real `InputArea`/`ChatStream`, tabs routing and hydration with an isolated in-memory command service. Three runtimes held 800 synthetic messages each. Both versions used the same updated renderer; only session/tabs/hooks sources switched between baseline HEAD and current code. Three initial hydration requests produced 3 → 1 transcript reads (809,058 → 269,686 bytes). Six real pane-header focus changes produced 6 → 0 reads (1,618,116 → 0 bytes), and 41 → 13 workspace commits. Both visible streams retained their distinct 30-update text; detaching through the real pane button and returning after 30 hidden updates kept the correct independent text and service-visible route. No page errors occurred. The browser used the same corrected message continuity route in both versions to isolate layout/hydration work; the service-path fixture above independently covers the main forwarding change. Full result: `test-results/session-performance/browser.json`.

Those browser DOM-settle samples were split 1,238 → 1,243 ms, six-focus sequence 1,572 → 1,068 ms, dual stream 668 → 825 ms, detach 652 → 865 ms, hidden return 585 → 692 ms. They include Playwright interaction and eight stable animation frames, development React and shared-workstation scheduling. The cold split and hidden return are not claimed faster. No actual sidecar or Electron IPC ran in Chromium.

The independent renderer fixture (`test-results/transcript-performance/summary.json`) found cold pinned transcripts first mounted historical rows before following the tail. Starting at the existing estimated tail preserves saved offsets and anchors while reducing split Markdown characters parsed 24,896 → 9,176 and layouts 13 → 4; background mount parsed 25,606 → 9,886 with layouts 15 → 4. Selecting only reasoning presence, rather than the growing reasoning string, reduced the live wrapper's renders 85 → 32 over 30 dual updates. Timings were noisy (split 746 → 561 ms; switch 546 → 565 ms; stream 793 → 1,173 ms), so reduced work, not general wall-clock speedup, is the supported result. Selection, unpinned scroll position, remount restoration, oldest history, expanded reasoning and all 40 ANSI tool-output lines remained accessible. Background-only updates caused zero transcript, live-wrapper or Markdown renders.

Regression coverage exercises same-visible focus, failed-core focus, rapid A+B → C → A+B → B supersession, concurrent hydration, in-place session changes, restart with the same session id, completed history/delta reconciliation, parked partial continuity, stopped-stream cleanup and visible ready metadata. The targeted session suite passed 184 tests across four files; the independent renderer suite passed 42 across two files. Shared TypeScript checking passed. Existing React-act and EventEmitter-listener test warnings remain visible; targeted formatting checks are recorded separately. No live profile or authenticated upstream request was used, no thresholds/defaults were changed, and the released checkout and running app were left untouched.

## Side questions and external browser

Factory's [CLI reference](https://docs.factory.ai/droid-cli/cli-reference#slash-commands) describes `/btw` as separate from the main conversation. The [September 28, 2026 release notes](https://docs.factory.ai/changelog/release-notes) confirm in-progress context, live tool calls, and per-question stop. They do not specify a read-only enforcement policy.

WISA passes the in-progress parent context and enables a separate `read_workspace_file` tool for compatible models in Agent tabs. Core registers only that tool for the side request and enforces its own argument and file checks; the general `read` tool also accepts URLs and MCP resources and is not exposed here. Reads are scoped to visible regular UTF-8 files in the project, up to six 16 KiB windows per question. Hidden paths, links, external URLs, shell, and mutation tools are denied. File excerpts go to the configured model provider; this is not a sandbox against hostile local processes. Tool results and intermediate replies are not saved in the main transcript; only billing metadata is journaled there. Parked tab responses stay with their origin, and invalidated runtimes discard late responses. Chat tabs and incompatible models use conversation context without reads.

Windows verification with the rebuilt sidecar and a localhost OpenAI-compatible fixture: the side request received the earlier conversation, advertised only `read_workspace_file`, and cited a value delivered by a real workspace read; the main transcript was unchanged. This verifies the RPC and file-read path, not the factual accuracy or tool compatibility of all models.

[Chrome DevTools MCP](https://developer.chrome.com/blog/chrome-devtools-mcp-debug-your-browser-session) and the [Playwright MCP extension](https://playwright.dev/mcp/configuration/browser-extension) can reuse an authenticated Chrome session, but add a separate connection and MCP surface. [Lightpanda](https://lightpanda.io/docs/core-concepts/what-is-lightpanda) uses a separate headless engine and cannot reuse a Chrome profile. WISA uses the existing [omp browser relay](https://github.com/can1357/oh-my-pi/tree/main/packages/browser-relay) only when explicitly configured, with no embedded Electron browser or automatic Chrome setup. Smaller outputs can save model context; using a different engine or transport does not by itself reduce token usage.
